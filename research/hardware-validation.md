# Hardware validation and traffic capture plan

Purpose: turn the static findings in this repo into observed facts with one camera and one phone. Everything else in `docs/` is static analysis; record results here (or in a dated file under `captures/`) with camera model, firmware version, phone model/OS and app version.

## 1. Equipment and setup

- Test camera: **GR IV HDF** (BLE model code 8, model string `RICOH GR IV HDF`). Its firmware file is byte-identical to GR IV and GR IV Monochrome, so results transfer to those bodies except where hardware differs (HDF filter, Monochrome image controls); see [camera models](camera-models.md). Note the firmware version from the camera menu; the image reports 1.20 for GR IV HDF.
- GR WORLD supports this body. **Image Sync does not**: its Bluetooth advert parser stops at model code 6 and its Wi-Fi support list has no GR IV string, so it cannot be used to generate reference traffic on this camera. Live view, HTTP shooting, exposure writes and BLE wake are therefore tested directly from the Mac (§3) or with a generic BLE tool, using the formats Image Sync uses on GR III.
- The camera's Bluetooth setting allowing connection while the power is off, for the wake test.
- A phone with GR WORLD installed, plus this Mac running the repo's GR Lab app and `gr` CLI (§1.1). nRF Connect (Nordic, free) is optional as an independent BLE tool.
- Pairing caution: bonding a second client (the Mac, nRF Connect) may change the camera's paired-device list. How many bonds the GR IV keeps is **[unknown]**; be prepared to re-pair GR WORLD afterwards.

### 1.1 Repo tools

| Tool | Run | Covers |
|---|---|---|
| GR Lab (`apps/gr_lab`, Flutter, `universal_ble`) | `cd apps/gr_lab && flutter run -d macos` | Scan with decoded adverts (model, serial, power); **BLE** = bare connect + GATT discovery, no writes; **Session** = full hand-off (wake if off and the switch is set, identity, credentials, WLAN-on, join with `networksetup`, `/v1/props` check, change WebSocket, 2 Hz liveness); BLE identity, credentials, clock sync, shutter, WLAN on/off, power off (confirmed); HTTP props/ping/photos |
| `gr` CLI (`packages/gr_cli`) | `dart run gr_cli:gr --help` from `packages/gr_cli`, with the Mac on the camera AP | Every HTTP route in [HTTP API](protocol/http-api.md) and [remote shooting](protocol/remote-shooting.md), `watch` for the change WebSocket, `liveview` frame statistics, `monitor` for the liveness rule. State-changing and firmware routes need `--force` |

Both write a JSON Lines trace of every BLE, HTTP and WebSocket exchange: GR Lab to `~/Library/Application Support/dev.gr.grLab/traces/trace-<UTC time>.jsonl` (path shown in the app), the CLI to the file given with `--trace`. The macOS app is not sandboxed so that `networksetup` can join the camera network; on other platforms it shows the SSID and password to join manually. The first scan triggers the macOS Bluetooth permission prompt.

### Mac

| What | How |
|---|---|
| BLE (HCI) without PacketLogger | bluetoothd writes its own PacketLogger file when `sudo defaults write /Library/Preferences/com.apple.MobileBluetooth.debug HCITraces -dict StackDebugEnabled -bool true HCIFileTraces -bool true` is set and bluetoothd restarted (`sudo killall bluetoothd`; Bluetooth input devices drop for a few seconds). The file is `/private/var/root/Library/Logs/Bluetooth/bluetoothd-hci-latest.pklg` (4 MB, 3 rotations). Copy it with an explicit path under `sudo` (`sudo cp /private/var/root/Library/Logs/Bluetooth/bluetoothd-hci-latest.pklg …`): a `*` glob is expanded by your own shell, which cannot list that directory. | Pairing key distribution override (test only) | `sudo defaults write /Library/Preferences/com.apple.MobileBluetooth.debug LE -dict OverrideInitiatorKeys -int 1`, restart bluetoothd; bluetoothd logs "Warning: Overriding initiator keys to 0x1". Applies to every new pairing on the Mac while set. |
| Reading `.pklg` | Records are big-endian: `u32 length` (of what follows), `u64 timestamp` (seconds and microseconds), `u8 type` (0 command, 1 event, 2 ACL sent, 3 ACL received, 0xFC/0xFD notes), then the HCI packet. In the files from this Mac the timestamps read 5 hours behind local time. SMP is L2CAP CID `0x0006`. |
| Logs | `log show --predicate 'process == "bluetoothd"'` gives "Using public address…", `localKeyDist`, "Pairing succeeded", "LE Link disconnected … reason N" (N = 700 + HCI reason for link-layer failures) and encryption status. |

On the Mac, `tshark`/Wireshark are not installed yet; they are needed only to read pcap captures.

## 3. Direct probes from the Mac (no phone capture needed)

Turn the camera's Wi-Fi on with GR WORLD (open its import screen) or with GR Lab: **Session** reads the SSID and passphrase over BLE (`90638E5A-…`, `0F38279C-…`), writes `01` to WLAN Control `9111CDD0-…`, joins the AP and checks `/v1/props`. The camera's hostapd template allows up to 255 stations, so the phone can stay associated ([network configuration](firmware-network-config.md)). Note the AP security mode the Mac reports (GR IV may advertise WPA3). Run read-only probes first; do the state-changing ones in the listed order and stop at the first unexpected result. Record HTTP status, body and the camera's visible state.

Read-only:

```sh
curl -sS -m 5 http://192.168.0.1/v1/props
curl -sS -m 5 http://192.168.0.1/v1/ping
curl -sS -m 10 'http://192.168.0.1/v1/photos'
```

Also open the change WebSocket in a second terminal for the whole session (`dart run gr_cli:gr watch`, or `websocat ws://192.168.0.1/v1/changes`) and keep its output. The CLI equivalents of the probes are `gr props`, `gr ping`, `gr photos`, `gr liveview`, `gr focus`, `gr shoot`, `gr params camera …` and `gr --force wlan-finish`; add `--trace <file>.jsonl` to keep the exact requests and responses.

State-changing, one at a time. Bodies are `key=value` sent as `text/plain` and not URL-encoded, exactly as Image Sync sends them ([remote shooting](protocol/remote-shooting.md)):

1. Live view for 30 s, saving the raw stream: `curl -sS -m 30 'http://192.168.0.1/v1/liveview' -o lv.raw`, then the same with `?maxfps=5`. Split on `FF D8`…`FF D9`; check that several distinct frames decode and note their resolution and the actual frame rate.
2. Touch focus: `curl -sS -m 10 -X POST -H 'Content-Type: text/plain' --data-binary 'pos=50,50' http://192.168.0.1/v1/lens/focus`; note the `captureId` and the WebSocket `lens` message.
3. Shutter: `curl -sS -m 10 -X POST -H 'Content-Type: text/plain' --data-binary 'af=on' http://192.168.0.1/v1/camera/shoot`; confirm the WebSocket `storage` `add` message and the new file in `/v1/photos`.
4. One exposure change: `curl -sS -m 10 -X PUT -H 'Content-Type: text/plain' --data-binary 'xv=+0.7' http://192.168.0.1/v1/params/camera` (pick a value from `xvList` in `/v1/props`); check the response props and the camera display. Repeat once while live view runs.
5. Last: `curl -sS -m 10 -X POST http://192.168.0.1/v1/device/wlan/finish`, then confirm the AP disappears and can be re-enabled over BLE.

Never send firmware upload/prepare, `/v1/debug/*`, factory USB ops, or `POST /v1/device/finish` (camera power-off) unless that is the test.
