# GR III / GR IV firmware network configuration

## Scope and evidence boundaries

Static inspection of the extracted **GR III 2.20** and **GR IV 1.20** INITFS images: boot dispatch, service and WLAN scripts, hostapd/DHCP templates, radio configuration, and selected native caller evidence. **No camera was booted, joined, or timed.** “Starts” below describes a demonstrated code path, not an observed successful launch. Configured settings are not captured beacons, DHCP offers, or effective driver state.

Source shorthand used throughout:

- **G3** = `firmware/gr3-root/firmware.bin_extract/initramfs_extract/gzip.uncompressed_extract/`.
- **G4** = `firmware/gr4-root/firmware.bin_extract/`.
- Paths following G3/G4 are relative to those roots; line numbers refer to extracted text. The finit and GR III objdump analyses use raw ELF linked addresses. Native decompiler addresses use their saved provider coordinates: GR IV netmgrd is rebased by `0x10000` and Thumb bit 0 is cleared. Neither coordinate is an outer-firmware file offset; explicit file offsets are labeled separately.

## 1. What starts the daemons

### Boot dispatch is not established merely by finding systemd or SysV files

The extraction manifests record `/init → sbin/finit` on both models. GR III additionally has `/sbin/init → ../lib/systemd/systemd`; GR IV has `/sbin/init → finit`. GR IV also ships `etc/inittab` and SysV runlevel links. Their presence alone does not choose the boot route.

The shipped **finit binaries themselves contain a direct service-table dispatch to `/etc/init.d/rc.local`**:

- G3 `sbin/finit`: child table at `0x21438`, record stride `0x28`; record 3 at `0x214b0` has command pointer at `+4` to `0x111b8`, the string `/etc/init.d/rc.local`. The child path builds argv at record `+8` and calls `execv` at `0x10c6c`. Disassembly evidence: `ev_1a0c6ef62be3e25da269b1094d94ac70fabed7361c3153e164d93bdea93a8de4`; binary SHA-256 `ebed9402b6e899943d2346ea8a31ba7323f46ff5777a925fbb53815d5d5bb0d1`.
- G4 `sbin/finit`: corresponding table at `0x12008`, record 3 at `0x12080`, command pointer `0x12f0`; Thumb instructions `0xc82`–`0xcfc` select the record and call `execv` at `0xcfc`. Binary SHA-256 `a7a2fb3204f29a3904578d57a90efc3d99a75944a008154d88f47694d0aa8b44`. The default objdump pass misdecoded Thumb as ARM; the call-path finding uses explicit Thumb decoding, not that invalid decode.

Reproducible offline inspections: `objdump -s -j .rodata -j .data <finit>` for tables/strings, `objdump -d <G3-finit>` for ARM instructions, and `objdump -d --triple=thumbv7-linux-gnueabi --start-address=0xc7c --stop-address=0xd04 <G4-finit>` with the installed LLVM objdump for GR IV. These commands inspect the files without executing them.

Both `etc/init.d/rc.local` wrappers set PATH to `/sbin:/usr/sbin:/bin:/usr/bin`, test `-x /etc/rc.local`, and execute it (lines 11–19). Both the `start` case and the default/no-argument case call `do_start` (22–35). Thus the finit table's no-argument invocation is sufficient; a runlevel argument is not required. This establishes a static boot chain through finit, while a real device's selected kernel/init invocation remains unobserved.

### Product startup scripts

**GR III — G3 `etc/rc.local`:14–49**

1. Sets `/dev/ttyUSI1` to 115200, starts syslog/klogd, logs component revisions.
2. Inserts `/home/root/murata-driver/bcmdhd.ko` (24).
3. Starts `CAMCTLD_LOG=info camctld -w &`, then polls `/tmp/camctld_ready` every 100 ms (26–29).
4. Starts `usbd &` and `SYSMGRD_LOG=info sysmgrd &` (31–32).
5. Reads `/tmp/startup_mode`; `restrict` exits before starting the network/BLE/web daemons (34–38).
6. Starts **`NETMGRD_LOG=info netmgrd &`** and **`BLESRVD_LOG=info bled &`** (40–41).
7. Waits for `/tmp/mounted`, then starts **`WEBAPID_LOG_LEVEL=info webapid &`** (43–46). A further `/dev/mtp_usb` wait precedes mtpd (48–49).

**GR IV — G4 `etc/rc.local`:14–197**

1. Builds a writable `/etc` overlay with upper/work directories under `/tmp/overlay`; the mount includes `noexec` (22–31). Shipped `/etc` bytes are therefore not necessarily the live writable view.
2. Logs revisions, enables UART hardware flow control, and conditionally exports GPIO 425 for the explicitly commented BT sleep-transition workaround (33–45).
3. Reads RTOS-provided region and fabrication values, selects regulatory domain and NXP modules/power configuration (47–170; §5 below). The `moal.ko` insertion is backgrounded in each recognized branch.
4. Starts `CAMCTLD_LOG=info /usr/bin/run_app /usr/bin/camctld -w &`, waits for `/tmp/camctld_ready`, then starts `/usr/bin/run_app /usr/bin/usbd &` and `SYSMGRD_LOG=info sysmgrd &` (172–178).
5. Reads `/tmp/startup_mode`; `restrict` exits before the remaining launches (180–184).
6. Starts **`NETMGRD_LOG=info netmgrd &`**, executes **`wait %1`**, then starts **`BLESRVD_LOG=info /usr/bin/run_app /usr/bin/bled &`** (186–190). In a recognized radio branch, the earlier backgrounded moal insertion is the first background job; the script does not name a PID in this wait.
7. Waits for `/tmp/mounted`, then starts **`WEBAPID_LOG_LEVEL=info /usr/bin/run_app /usr/bin/webapid &`** (192–194); `/dev/mtp_usb` gates mtpd (196–197).

`run_app` is a native executable, not a shell service declaration. This inspection establishes its argv and call sites, **not** restart, supervision, or watchdog semantics. Neither product `rc.local` directly starts hostapd or udhcpd. `webapid` is boot-launched after storage readiness, not launched by `start_wlan.sh` on every AP start.

### WLAN launch and stop

G3 `usr/bin/start_wlan.sh`:2–50 selects radio paths, generates entropy, then launches hostapd via:

```sh
start-stop-daemon -x /usr/sbin/hostapd -p /var/run/hostapd.pid -b -m -o -S -- /etc/hostapd-wpa2psk.conf -e /tmp/entropy.bin
```

G4 `usr/bin/start_wlan.sh`:14,23–54 uses the same launcher flags but passes **`/tmp/hostapd.conf`**, without the entropy option. The old Broadcom firmware/entropy assignments and old hostapd command are **commented out**, not a second active path (4–21,27).

Both then configure the AP address and invoke:

```sh
start-stop-daemon -x /usr/sbin/udhcpd -p /var/run/udhcpd.pid -m -o -S -- -S -a 0
```

The `--` separates launcher options from udhcpd's `-S -a 0`. No DHCP config filename is supplied. **That does not mean configuration-file reading is disabled.** This is an implicit-default-config invocation, not an explicit `/tmp` config generation path. The shipped `/etc/udhcpd.conf` supplies the settings documented in §3; a live offered lease was not observed.

GR IV native caller proof: `gr4-netmgr-device-start.c`:106–147,438,547–575, `netmgr::WlanDevice::Start` at `0x1f608`, evidence `ev_f57f46055c70bc061fbcec1b717fecdb2368fb4e93d0a1b2a12c2c85b594dba7`, copies/edits the config then invokes `Command::Exec` with `start_wlan.sh ap` for mode 0 or `start_wlan.sh sta` otherwise. Its native `Stop` builds the corresponding `stop_wlan.sh ap|sta` and executes it (`gr4-netmgr-device-stop.c`:149–179, address `0x1e540`, evidence `ev_43fa1ff0dc5f866ba9704fb34ae2c9bfa0e63d18bc2bfffb83a7870184040535`). Both records concern netmgrd SHA-256 `33dc04843893256e4d7137bd2661b1e9702253c53eb09ff8700a0ae4581bcd40`.

**GR III native caller proof:** G3 `usr/bin/netmgrd`, SHA-256 `97b8b715a1e4180a975a5f0c3bb79c9c6a375778b871e8296d10bbc11f0be912`, `WlanDevice::Start` at raw address `0x21670`, calls its config helper at `0x204dc` before constructing `start_wlan.sh ` (`0x21744`–`0x21754`). Mode 0 appends `ap`; the other branch appends `sta`; `Command::Exec` is called at `0x217a8`. `WlanDevice::Stop` at `0x20a68` similarly builds `stop_wlan.sh ap|sta` and calls `Command::Exec` at `0x20b5c`. These are direct disassembly/call-and-literal observations, not merely matching strings. Reproduce with `objdump -d --start-address=0x21670 --stop-address=0x21b44 <G3-netmgrd>` and `--start-address=0x20a68 --stop-address=0x20c30`; `.rodata` strings are at `0x360c8` (start), `0x35f48` (stop), `0x35f58` (`ap`) and `0x35e88` (`sta`, a suffix of another literal).

GR III's upstream `WlanCommandHandler::RecvChangeWlanRunningState` at raw `0x282c0` also resolves the request edge: request 0 branches to `WlanDevice::Stop` at call site `0x28334`; request 1 calls `Start(0)` (AP), while other nonzero requests call `Start(1)` (station) at `0x28318`. The station request therefore reaches the helper's explicit unsupported-mode failure. The whole small handler was inspected with `objdump -d --start-address=0x282c0 --stop-address=0x28350 <G3-netmgrd>`. This is a requested-state transition, not an idle-timeout decision.

The companion [native protocol inventory](firmware-protocol-inventory.md#additional-rea-native-findings) provides the upstream GR IV request dispatch: `RecvChangeWlanRunningState` routes zero to `Stop` and nonzero to `Start`; the manager worker also calls `Stop` on shutdown. This demonstrates requested transitions, not an autonomous inactivity threshold.

Both helpers reject the exact `sta` argument with `Not support station mode yet` and exit 1. A packaged station firmware/config or native ability to construct `sta` is **not** proof that this script supports station operation.

Both stop scripts stop udhcpd, stop hostapd, lower the AP interface, and poll `hostapd_cli status` until failure (G3 `usr/bin/stop_wlan.sh`:8–23; G4:8–24). They do not kill `webapid`, `bled`, or `netmgrd`. The shared `usr/bin/shutdown.sh`:8–23 instead handles product shutdown: in normal mode it sends **USR1 to webapid**, kills bled/netmgrd/loggers, unmounts storage, then waits indefinitely for `/tmp/bled_shutdown`. The trigger for calling that shutdown script is separate from the actions in it; it is not an idle timer.

## 2. Templates versus generated AP configuration

### GR III selected shipped file

G3 `etc/hostapd-wpa2psk.conf`:1–20 contains:

- `interface=wlan0`, `driver=nl80211`, control socket `/var/run/hostapd`, control group 0.
- `ssid=HOSTAPD_AP`, `hw_mode=g`, `channel=6`.
- `wpa=2`, `wpa_key_mgmt=WPA-PSK`, `wpa_pairwise=CCMP`, `rsn_pairwise=CCMP`, `wpa_passphrase=12345678`.
- `beacon_int=100`, `dtim_period=2`, `max_num_sta=255`, `rts_threshold=-1`, `wmm_enabled=1`, `ignore_broadcast_ssid=0`.
- Syslog logger mask `-1`, level `2`.

These are **shipped seed values**, not recovered credentials for a particular camera. GR III's native `WlanDevice::Start` calls `getenv("NETMGRD_HOSTAPDCONF")` at `0x21700`–`0x21710`; when absent, it uses `/etc/hostapd-wpa2psk.conf` (literal `0x360ac`, default branch `0x219f8`–`0x21a0c`). Both paths pass the selected filename to helper `0x204dc`.

That helper obtains camera properties **`0x1d` (channel), `0x1f` (SSID), and `0x20` (passphrase)**, constructs `HostapdConf` for that filename, calls `Read` at `0x20684`, and updates `channel` at `0x206c4`, `ssid` at `0x2070c`, and `wpa_passphrase` at `0x20740`, then calls `HostapdConf::Write` at `0x2075c`. The string literals are respectively `0x35efc`, `0x35f08`, and `0x35f10`. Reproduce with `objdump -d --start-address=0x204dc --stop-address=0x20924 <G3-netmgrd>` and `objdump -s -j .rodata <G3-netmgrd>`. No band/security/inactivity-key edit is present in this helper's recovered update path.

Consequently, **GR III rewrites its selected hostapd file in place; it does not use GR IV's band-template-to-`/tmp/hostapd.conf` workflow.** The observed `rc.local` launch does not set `NETMGRD_HOSTAPDCONF`. The native override changes its writer path, while the shipped shell helper still hardcodes `/etc/hostapd-wpa2psk.conf`; do not assume an arbitrary override is automatically propagated to hostapd. Property retrieval failures are logged and return from the helper; successful runtime writing or retrieved property values were not observed on hardware.

The WLAN shell script itself creates only `/tmp/entropy.bin` for this setup (initial byte `02`, then 20 bytes from `/dev/urandom`, `start_wlan.sh`:12–20). Unlike the native writer, the script does not edit hostapd configuration. The writer/helper distinction is why the literal `HOSTAPD_AP`, `12345678`, and channel 6 must not be reported as a camera's effective credentials/channel.

G3 `etc/hostapd-open.conf`:1–21 is a separate open configuration: channel 1, `max_num_sta=4`, `rts_threshold=2347`, and WPS/device-description fields. The shown WLAN script does **not** select it. Do not substitute its station limit or channel for the WPA2 file. The presence of generic `etc/wpa_supplicant.conf` likewise does not override the helper's station-mode rejection.

### GR IV band templates and native generation

The following are actual copy sources, not merely examples. G4 `etc/hostapd_24GHz.conf`:1–23 and `etc/hostapd_5GHz.conf`:1–27:

| Setting | 2.4 GHz copy source | 5 GHz copy source |
|---|---|---|
| Interface/driver | `uap0` / `nl80211` | Same |
| Control interface/group | `/var/run/hostapd`, 0 | Same |
| Mode | `hw_mode=g` | `hw_mode=a` |
| Channel | `channel=0`, `chanlist=1 6 11` | `channel=0` |
| HT | `ieee80211n=1`, `[SHORT-GI-20]` | `ieee80211n=1`, `[SHORT-GI-20][SHORT-GI-40][HT40+]` |
| VHT | Not explicitly configured | `ieee80211ac=1`, `vht_oper_chwidth=1`, `[SHORT-GI-20][SHORT-GI-40][SHORT-GI-80]`, center-segment index 0 |
| HE | `ieee80211ax=1`, `he_oper_chwidth=0` | `ieee80211ax=1`, `he_oper_chwidth=1`, center-segment index 0 |
| Beacon / station limit / WMM | `beacon_int=100`, `max_num_sta=255`, `wmm_enabled=1` | Same |
| Security seed | `wpa=2`, `wpa_pairwise=CCMP`, `wpa_key_mgmt=SAE WPA-PSK`, `ieee80211w=1`, `sae_require_mfp=0`, `auth_algs=1` | Same |
| Credential seed | `GR_000000`; WPA passphrase and SAE password `12345678` | Same |

The security seed is WPA2/WPA3 transition configuration: hostapd's `wpa=2` denotes RSN, **not “WPA2 only” when SAE is also selected**. `ieee80211w=1` is optional management-frame protection in the seed. These values are subject to native editing and are not a guarantee of the selected runtime security mode.

The native generator reads camera properties for channel, SSID, password, band, and security. It selects the 5 GHz file when the band value is 1, otherwise the 2.4 GHz file, copies it to `/tmp/hostapd.conf`, reads it into `HostapdConf`, edits it, and calls `Write` before launching the helper (`gr4-netmgr-device-start.c`:106–147,217–438). Edits include:

- Channel, SSID, WPA passphrase and SAE password.
- Security-dependent `wpa_key_mgmt`, `ieee80211w`, and `sae_require_mfp`; WPA/SAE credential removal and a long-PSK branch; an additional branch removes security keys (239–349). The presence of that branch alone does not establish an exposed camera setting.
- For 5 GHz, HT capability and VHT/HE center-segment indexes based on channel (350–432). Thus template index 0 is not a recovered operating center channel.
- For non-5-GHz operation with a nonzero selected channel, removal of `chanlist` (433–436).

The security branch values can be resolved by pairing the saved pseudocode (246–345) with `objdump -s -j .rodata <G4-netmgrd>`: raw addresses `0x21d9c`, `0x21da0`, `0x21da4`, `0x21da8`, `0x21dac`, and `0x21db0` contain `0`, `SAE`, `2`, `1`, `SAE WPA-PSK`, and its suffix `WPA-PSK`. These are the decompiler's `0x31d…` literals before its `0x10000` rebase.

| Camera security property `0xbc` | Generated `wpa_key_mgmt` | `ieee80211w` | `sae_require_mfp` | Credential handling |
|---|---|---|---|---|
| 0: WPA2 | `WPA-PSK` | 0 | 0 | Removes `sae_password`; for a password longer than 63 bytes, replaces `wpa_passphrase` with `wpa_psk` |
| 1: WPA3 | `SAE` | 2 (required PMF) | 1 | Removes `wpa_passphrase`, retains `sae_password` |
| 2: transition | `SAE WPA-PSK` | 1 (optional PMF) | 0 | Retains WPA and SAE password keys |

The property-read failure falls back to 0; unrecognized values other than `0xffffffff` also take the WPA2 branch. The `0xffffffff` branch removes `wpa`, pairwise/key-management/credential/PMF fields and `auth_algs`; it is code for an unsecured configuration, not proof of a user-accessible open-AP option. No runtime-selected property value or successful association was observed.

The same literal resolution gives 5 GHz center-segment values **42** and **155** (`0x21e4c`, `0x21e50`). The generator assigns 42 for selected channels in 36–48 and 155 for 149–161; it selects HT40+ for 36/44/149/157 and HT40− for 40/48/153/161. These are configured branch outputs, not a measured supported-channel list. Channel 0 follows a separate automatic-channel path; the zero-valued template must not be mistaken for a physical RF channel.

There is no inactivity/disassociation override among those shown key edits. Other native functions, driver defaults and the radio firmware are not thereby proved free of such behavior.

G4 `etc/hostapd_sample.conf`:1–18 is **not** the selected copy source: it has fixed channel 6, WPA-PSK only, `dtim_period=2`, RTS `-1`, and explicit `rsn_pairwise=CCMP`. In particular, neither active band template explicitly sets `dtim_period`; importing the sample's value of 2 into a description of the generated runtime config would be wrong. The remaining default behavior requires the shipped hostapd implementation or a runtime dump.

## 3. Addressing and DHCP duration

G3 `start_wlan.sh`:30 and G4:33 assign **192.168.0.1, netmask 255.255.255.0** to their AP interfaces. This is `192.168.0.0/24`, consistent with the app's HTTP/WebSocket address in [the HTTP API report](protocol/http-api.md).

Both `etc/udhcpd.conf` files have the following **uncommented** settings (5–11,87–92):

```text
start 192.168.0.2
end   192.168.0.10
interface wlan0   # GR III; uap0 on GR IV
option subnet 255.255.255.0
option lease 3600
```

- Lease duration is **3600 seconds = one hour**. The trailing `# 10 days of seconds` is stale and contradicts the numeric value; it must not be used as the duration.
- The pool has nine addresses. That is distinct from the hostapd template's 255-station association limit.
- Router and DNS examples are commented out (86–91). The file does not explicitly advertise an internet gateway or DNS server through those examples.
- `#auto_time 7200`, `#decline_time 3600`, `#conflict_time 3600`, `#offer_time 60`, and `#min_lease 60` are comments/default descriptions (29–55), not active overrides. They are also different concepts from an AP inactivity timer.
- The header says “Sample udhcpd configuration file,” but the file contains active camera-subnet settings. A sample-derived header does not make the file unused. Conversely, absence of an explicit filename in the launch command is not by itself a readback of the daemon's loaded configuration.

No `/tmp/udhcpd.conf` generation is present in the inspected startup scripts. Actual leases, client renewals, DHCP default-path resolution, and any native mutation of the config were not captured on a camera. Lease expiry does not, by itself, establish Wi-Fi disassociation or AP shutdown.

## 4. Timing, inactivity, and power-save distinctions

### Finite startup/stop checks versus unbounded boot gates

| Check | Static behavior | What it does **not** establish |
|---|---|---|
| G3 AP start | 30 iterations, sleep 100000 µs then query `wl bss`; require exact `up` (`start_wlan.sh`:36–48) | Not a session idle timeout |
| G4 AP start | Same sleep/count, require `hostapd_cli -i uap0 ping` → `PONG` (39–52) | Not an HTTP/WebSocket ping or client keepalive; control-socket responsiveness is not a captured beacon/association |
| AP stop, both | Up to 30 `hostapd_cli status` checks; sleep 100 ms while it succeeds; error if never failing | Not a client inactivity detector |
| Camera-controller readiness | `/tmp/camctld_ready`, 100 ms polling, no loop count | No three-second upper bound on boot or WLAN-on-to-ready |
| Storage readiness | `/tmp/mounted`, 100 ms polling, no loop count | No bound on webapid startup |
| MTP readiness | `/dev/mtp_usb`, 100 ms polling, no loop count | Not a network timeout |
| G4 `wait %1` | Background-job completion wait, no timeout in script | Not a fixed BLE or WLAN startup duration |
| Product shutdown | `/tmp/bled_shutdown`, 100 ms polling, no loop count | Not an idle shutdown countdown |

Three seconds is the **aggregate explicit sleep budget** of 30 × 100 ms; command execution and scheduling add time. It is not a rigorous wall-clock deadline. Failure branches exit without an explicit rollback sequence in the start helper; this report does not infer what the native caller subsequently cleans up.

### Explicit power-related configuration

- **GR III:** WLAN startup writes firmware/NVRAM/CLM paths to `/sys/module/bcmdhd/parameters/` (15–17). No `wl pm`, `wl mpc`, `iw ... power_save`, or `iwconfig ... power` toggle is present in the inspected WLAN start/stop scripts. The selected NVRAM's `lowpowerrange2g=0` / `lowpowerrange5g=0` (77–78) are radio calibration/configuration fields, not an established AP auto-off interval. `bcmdhd.ko` declares a `dhd_idletime:int` module parameter; a parameter name does not reveal its selected value or prove a station-disconnect policy.
- **GR IV:** the active **`SDIW612` block** of `lib/firmware/nxp/wifi_mod_para.conf`:141–153 sets `ps_mode=1`, `auto_ds=1`, `host_mlme=1`, `drv_mode=0x3`, `dev_cap_mask=0xFFFFEFFF`, `cfg80211_wext=0xf`, `max_vir_bss=1`, `cal_data_cfg=none`, `mcs32=0`, `country_ie_ignore=1`, and `fw_name=nxp/sduart_nw61x_v1.bin.se`. The file contains other chip blocks; driver selection is not proven solely by the block name. The matching NW61x payload is packaged.
- Shipped `moal.ko` `.modinfo` descriptions establish the meanings of the two power values: **1 enables IEEE PS mode; 1 enables auto deep sleep**. They also describe `drv_mode` bit 0 as STA and bit 1 as uAP, so `0x3` enables those driver roles; that does not undo the shell helper's station rejection. These are driver settings, **not evidence that an associated AP turns off after X seconds**.
- The generic **commented USB8997 example** in that same file includes `#auto_ds=0`, `#ps_mode=1`, `#pm_keep_power=0`, `#shutdown_hs=1`, `#low_power_mode_enable=1`, `#wakelock_timeout=10`, `#hs_wake_interval=400`, `#disconnect_on_suspend=0`, `#GoAgeoutTime=0`, `#multi_dtim=0`, and `#inact_tmo=0` (155–214). None is an active SDIW612 override. In particular, do not report an inactivity timer of zero, a ten-second wake-lock timeout, or a suspend-disconnect policy from these comments. The module describes `inact_tmo` as an IEEE power-save inactivity timeout, without establishing the active value.
- G4 `etc/rc.local`:14–18,43–45 explicitly enables **BT module sleep-transition failure detection** and exports GPIO 425. The comment describes a chip failure to *enter* sleep. It supplies no WLAN auto-off interval and does not establish a cause of Wi-Fi session loss.
- G4 `usr/bin/ble_enable.sh`:15–38 optionally unbinds/rebinds `1b000000.mmc`, waits **2 seconds**, temporarily attaches HCI at 115200 with flow control, selects a board-specific `bt_power_config_ALL.sh`, sends vendor HCI command `0x3f/0x0009` with `c0 c6 2d 00`, waits **50 ms**, sets UART to 3000000, lowers hci0 and kills hciattach. These are bring-up operations, not periodic WLAN keepalives. For moal, `ps_mode` description is at file offset 494561, `auto_ds` at 494899, and `inact_tmo` at 488756. This evidence parses metadata only, not runtime parameter values or driver control flow.

### Bounded negative findings

Text searches across both extracted roots for `ap_max_inactivity`, `skip_inactivity_poll`, `disassoc_low_ack`, keepalive variants, explicit power-save commands, inactivity/ageout/suspend settings, plus direct reads of the selected AP templates and WLAN helpers, found **no explicit AP inactivity/disassociation interval or periodic Wi-Fi application keepalive in these files**. The commented NXP options above are the relevant near-matches. G3's commented systemd `IdleAction` / `IdleActionSec` examples are not product WLAN policy.

This is **not** a claim that hostapd lacks compiled defaults, firmware lacks station aging, or the RTOS never disables WLAN. It does not establish an effective 300-second hostapd timeout, an infinite timeout, a TCP keepalive interval, or a server-side WebSocket ping policy. Those require their own implementation/runtime evidence. Link-layer power saving, per-station aging, DHCP renewal, TCP connection reuse/keepalive, application liveness probes, and whole-camera/AP shutdown must remain separate.
