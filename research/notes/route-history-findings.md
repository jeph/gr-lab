# Historical evidence for the ten extra GR HTTP routes

Research date: 2026-11-07. Public-source research only; no camera requests, tests, firmware execution, or shared MCP use. Existing documentation was not edited. Methods below use `http://192.168.0.1` unless stated otherwise.

## Bottom line

- **GR III/IIIx:** Ricoh explicitly documents Image Sync Live View, exposure control, touch AF and remote capture. GR III remote capture arrived in **Image Sync 2.0.5, 2019-08-08**, requiring camera firmware 1.10 or later. Image Sync 2.0.4 (2019-04-23) had only image browsing/transfer. This is a real historical product distinction, not a timeless capability assertion. [1][2]
- **GR WORLD:** the current FAQ says **“No. Live View is not supported in the app.”** It also says **“Exposure adjustment operations are not supported.”** Remote shooting on GR IV/III/IIIx releases the shutter **using Bluetooth**; single-frame and self-timer are supported, but continuous/bracket/multiple-exposure/interval/interval-composite, bulb/time exposure and video are not. These are **app limitations**, not proof that firmware HTTP handlers cannot work. [3]
- **GR IV:** there is now stronger evidence than legacy endpoint inheritance: a dated third-party GR IV log records `/v1/liveview?maxfps=7` opening and decoded/rendered **720×480 JPEG frames**, approximately 7 fps before an orientation-driven reconnect. That client uses **BLE shutter** on IV. This does **not** prove IV HTTP shoot, focus or exposure writes. [8][9]
- All ten method/path pairs already appeared in **GR IIIx firmware strings reported on 2022-06-16**. That author explicitly reports liveview JPEG output after camera experiments, but “I pointed curl at most of these” does not individually validate the other nine routes or their payloads. [5]

Evidence labels: **O** official product documentation; **C** inspected request-generating client code; **R** published real-camera observations/logs (not reproduced here); **S** static firmware/schema/resource evidence only. Confidence is claim-specific: a high-confidence code callsite is not a high-confidence compatibility guarantee.

### Exact GR II transport distinction

The official live app remains readable on Ricoh's server, not merely in a third-party mirror. `gr-app.js::_callAPI` splits its input at `?`; `grist.js::post` supplies the suffix as AJAX `data`, using jQuery's default form content type. Object data is serialized with `$.param` and then `decodeURIComponent`, so e.g. `pos=50,50` is sent literally. The UI command sequencer also splits `&`: `put=params/camera?av=2.8&cmd=mode refresh` is a PUT body `av=2.8` followed by a separate command, not a combined camera-parameter payload. The normal shutter calls `shoot` with `af=camera`; on `errMsg == "Precondition Failed"` it falls back to `shoot/start` with that body, and `shoot/finish` ends the held operation. These are GR II client behaviors, not a GR IV contract. [4]

Image Sync's manual explicitly lists III/IIIx alongside shutter speed, aperture, ISO, EV and white-balance controls, AF-only or AF+shoot at the touch position, and Live View on/off. It says capture is unavailable with drive modes other than single frame or an HDMI cable connected; turning Live View off enables operation on the camera. Its supported-model list contains II/III/IIIx, **not IV**. [1][2]

GR IV's own FAQ specifies GR WORLD Bluetooth shutter with immediate, 2-second or 10-second release; Wi-Fi is used for image transfer, and is disabled with AV equipment, video mode or USB connection. USB-C DisplayPort Alternate Mode live output is a different facility from HTTP Live View. [12]

## Stronger IV evidence, and why it remains bounded

The 2026-10-09 StickS3 smoke report and associated raw log are substantially stronger than a README assertion: they provide the request path, real JPEG dimensions, increasing stream/render counts, throughput and reconnect times. An initial black display was attributed to the controller's failed canvas allocation; after reset the user confirmed pictures on-screen. The report does not establish its root cause, long-term stability, every camera firmware, or HTTP shutter success. The logged WLAN finish is transmission-only. [8]

The predecessor `RicohViewfinder` says it was verified specifically on **IV HDF** but was deprecated because sustained BLE+Wi-Fi liveview caused significant camera heating; its README explicitly excludes III/IIIx from that implementation. This is an author hardware report, not our measurement. [13]

GR4-WebCam contains genuine UI request callsites for liveview (`?maxfps=15&reso=720x480`), bodyless HTTP shoot and form exposure PUTs. However, it requires **modified GR IV 1.11 firmware**, manually launches hostapd/udhcpd and a port-8080 BusyBox proxy to the camera's native port-80 API. It supplies no comparable published raw success trace for those writes. Its README's “focus”/“file format” UI claims exceed the inspected editable `CTRL` list, which has exposure/WB/effect/metering/drive but no focus-write control. Thus it is a useful implementation lead, **not stock-IV focus/exposure validation**. [10]

A separate 2026-10-12 report identifies **GR IIIx firmware 1.50** and `GET /v1/liveview?maxfps=7&reso=720x480`; one **BLE** shot was followed by a camera lockup requiring battery removal. Explicit resolution and newly subscribed BLE notifications were confounded; the report does not establish which caused it. This cautions against treating successful liveview/shoot combinations as universally safe. [14]

## Additional GR III client-source corroboration

[Nielk74/ricoh-gr3-android, `CameraHttpClient.kt`](https://github.com/Nielk74/ricoh-gr3-android/blob/main/app/src/main/java/com/ricohgr3/app/wifi/CameraHttpClient.kt) is direct **C-level** evidence beyond a README: `liveview()` constructs a bare GET `/v1/liveview` and passes the response stream to `MjpegFrameParser`; `shoot()` constructs POST `/v1/camera/shoot` with an empty byte-array body; `setCameraParams()` sends PUT `/v1/params/camera` using OkHttp `FormBody` from `CaptureParams.toFormFields()`; `ping()` GETs `/v1/ping`. These requests have no query parameters. The source targets GR III and explicitly roots the URL at `http://192.168.0.1/v1/`. Its comment “shoot takes no params” is the author's assumption, **not** a server contract: the older official GR II source demonstrably supplies parameters. No older release date or route-by-route successful hardware trace was established for this Android code, so it must not be dated to Image Sync's 2019 release or treated as IV validation.

The [ShengZhou-dev GR III adaptation](https://github.com/ShengZhou-dev/RICOH-GR3-Live-View-Shooting) reports testing on GR III firmware 2.00 and closing/reopening Live View around focus. Its preview-service source calls `_api->focus()`, but the exact focus implementation could not be retrieved in this research; no payload is inferred from that method name. Thus the bare-focus `pos` body in the table remains schema evidence, not independently verified GR III wire traffic.
